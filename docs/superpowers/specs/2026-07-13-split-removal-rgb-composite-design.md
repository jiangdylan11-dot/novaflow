# Split Removal RGB Composite Design

## Status

Approved for implementation on 2026-07-13 after read-only investigation of the locked `4783` surface and two existing Removal runs.

## Requirement

`去除物体` must replace the selected object with the background generated by Removal V4. It must not turn the selected area into a black block or transparent hole. Current replacement-layer behavior remains unchanged: a successful result creates one replacement layer and hides the source layer.

## Confirmed Root Cause

The Removal V4 workflow is healthy. Prompt `6dc07c77-c98b-49b4-bd49-aaeefc8076ac` produced an opaque `512x640` RGB result in which the axe was removed and the background was reconstructed. The masked region contained zero near-black pixels.

The renderer then passed that complete RGB result through `runRmbgCutout()`. Prompt `e63e0ce3-e550-4245-8ecd-2b7b0a729a75` kept the RGB but changed most background pixels to low alpha. Inside the user mask, `94.155%` of pixels had alpha at or below `8`. `mergeRemovalInpaintResult()` converted those pixels to `RGBA(0,0,0,0)`, then `executeInpaintTool()` hid the source layer. The transparent hole therefore exposed the dark canvas background.

This is a regression of the same failure recorded in commit `9c4d78e58`. The safe helper `compositeRemovalRgbResult()` still exists but is no longer called after commit `90657caa` restored the old replacement-layer path.

## Architecture

Keep Removal V4, its models, mask polarity, prompt, sampler, and `outputMode: 'replacement'` unchanged. Change only Removal result post-processing:

1. Decode the successful `VAEDecode -> SaveImage` output as the result crop.
2. Call the existing `compositeRemovalRgbResult(layerOriginalCanvas, resultCropCanvas, crop.cropMask, crop.cropBox)` helper.
3. Blend generated RGB only inside the hard selection mask, retaining the helper's existing inward `8px` feather.
4. Build the same full replacement layer, return `replacementForPartId: part.id`, and keep the existing source-hide state transition.
5. Never call RMBG from `mergeRemovalInpaintResult()`.

Normal Completion/Edit still use `mergeInpaintResult()` and retain their generated-foreground/RMBG behavior. Object extraction and every other RMBG consumer remain unchanged.

## Files

- `particle-editor/spine-split-runtime.js`: remove the Removal-only RMBG branch and use the existing RGB composite helper.
- `scripts/check-split-removal-result-contract.mjs`: lock route isolation, no-RMBG Removal post-processing, replacement semantics, and zero cleared pixels.
- `package.json`: expose `check:split-removal`.
- `logs/debug.log`: record the bug, cause, solution, and exact scope.
- Runtime mirrors: generated only by `npm run sync:runtime`.

## Error and State Behavior

- A failed Removal workflow still fails before committing a layer.
- A successful Removal result no longer depends on RMBG availability or alpha quality.
- `replacementForPartId`, source hiding, active-layer selection, preview refresh, split-set sync, and temporary cache refresh remain unchanged.
- Debug evidence records the raw Removal RGB, effective merge mask, final replacement preview, and `postprocess: 'removal-rgb-mask-composite-no-rmbg'`.

## Risks

- Mask-edge seams: retain the existing `8px` feather and validate rather than retuning it in this fix.
- Transparent source layers: generated RGB may make selected transparent pixels opaque. This is consistent with background reconstruction, but both opaque and transparent-layer cases must be checked.
- Route spillover: contracts must prove `mergeInpaintResult()` still retains its existing logic while only `mergeRemovalInpaintResult()` loses RMBG.
- State regression: contracts and live acceptance must prove the source layer is still hidden only after the replacement layer commits.
